# A Joint LLM and Optimization Agent Solution for Drone Scheduling in Victim Search Missions

Reference implementation accompanying the manuscript *A Joint LLM and
Optimization Agent Solution for Drone Scheduling in Victim Search Missions*.

## Overview

The system places an agent at a ground control station (GCS) to schedule a
fleet of energy-constrained UAVs over repeated search cycles. Each decision
has two stages:

1. **LLM reasoning:** infer plausible locations of the unfound travelling
   groups from clues, terrain, mobility knowledge, elapsed time, and search
   history, then produce a cell-priority vector `w(t)`.
2. **Constrained assignment:** retain energy-feasible cells, select the top
   `B` candidates, and solve a bottleneck assignment that minimises the
   worst-case UAV travel time.

The repository contains the simulator, the proposed policy, six conventional
baselines, four LLM-based comparison/ablation conditions, and the drivers for
all five experiments.

## Installation and Offline Preflight

Python 3.9 or later is supported; the validated environment uses Python 3.9.6.

```bash
git clone <repository-url>
cd <repository-directory>
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
./run_all.sh --preflight
```

The preflight does not load API credentials or call a model. It checks the
dependencies, regression tests, 116-run manifest, five experiment entry
points, and analysis entry point. A successful run ends with `PREFLIGHT VALID`.

## Experimental Setup

### Scenario and search parameters

The simulated search area is `7 km × 7 km`, divided into a `28 × 28` grid
with eight terrain types. It contains GCS/Entry, Trail Fork, Overlook, Caves,
Pond, and Campsite landmarks; impassable cells cannot be searched.

Five missing people travel in three groups: Family A (an adult and a
seven-year-old child), Family B (two moderately fit adults), and Youth C (an
experienced solo hiker). Their last sighting at Trail Fork defines `t = 0`.
The UAV search starts after a `3,600 s` response delay. Ground-truth victim
trajectories are generated by the simulator and never exposed to a policy.

Cell-search times are `50`, `60`, `60`, `70`, `80`, `100`, and `120 s` for
trail, meadow, pond, creek, sparse vegetation, rocky terrain, and dense
forest, respectively.

### UAV configuration

The main experiments use `N = 10` UAVs and dispatch batch size `B = 10`.
Each UAV has `500 kJ` initial energy, a `30 kJ` reserve, `15 m/s` cruise
speed, `200 W` flight power, and `150 W` search power.

Detection parameters `(p_d, p_f)` are `(0.95, 0.02)` for meadow, trail,
creek, and pond; `(0.80, 0.05)` for sparse vegetation; `(0.55, 0.10)` for
dense forest; and `(0.65, 0.12)` for rocky terrain.

### Retrieved knowledge and prompt

The retrieved knowledge `R` contains category-specific on-trail/off-trail
walking speeds and stamina ranges:

| Category | On trail (m/s) | Off trail (m/s) | Stamina (km) |
| :--- | :---: | :---: | :---: |
| Child | 0.4–0.7 | 0.2–0.4 | 4–5 |
| Average adult | 0.7–1.0 | 0.4–0.6 | 6–9 |
| Experienced hiker | 0.9–1.3 | 0.6–0.9 | 15–30 |

It also includes water-seeking and physical-reachability heuristics. The
system prompt combines the role, two-stage task instructions, map and clue
context, retrieved knowledge, and JSON schema. Each cycle's user prompt adds
the current mission time, unfound groups, confirmed-victim reports, current
UAV state, occupied cells, and accumulated detection history. The LLM returns
the top `K' = 50` cell priorities; omitted cells receive zero priority.

### Timing definition

`agent_computation_times` records the end-to-end duration of each policy call:
prompt construction, LLM calls and permitted retries, parsing, feasibility
filtering, and assignment. `total_agent_computation_time` is their sum.

Checkpoint replay restores the saved duration of each policy call. UAVs that
are already executing an assignment continue to advance while the next
decision is computed; an idle UAV receiving a new assignment departs only
after that decision is ready. Consequently, `mission_completion_time` is read
from the computation-aware event clock, while agent computation time is also
reported separately and is not added to mission time a second time.

## Methods and Experiment Matrix

### Exp. 1: main comparison — 35 runs

Each row uses seeds 42–46 and `N = B = 10`.

| Code identifier | Description |
| :--- | :--- |
| `lawnmower` | Fixed systematic sweep |
| `greedy_coverage` | Nearest unsearched-cell coverage |
| `bayesian_search` | Uniform initial prior with Bayesian observation updates |
| `clue_prior_sweep` | Clue-derived initial prior used to order a fixed sweep |
| `clue_prior_greedy` | Fixed clue-derived initial prior with greedy dispatch |
| `clue_prior_bayes` | Clue-derived initial prior with Bayesian observation updates |
| `ours` | LLM priority inference plus energy filtering and bottleneck assignment |

The clue-derived prior is constructed once from the initial clues; it is not
an agent that reinterprets the observations with an LLM every cycle.

### Exp. 2: comparison and ablations — 20 runs

The four conditions are `llm_direct`, `no_rag`, `no_cot`, and
`no_bottleneck`, each over seeds 42–46 with `N = B = 10`. `llm_direct` asks
the LLM to output UAV-cell assignments directly. The first two component
ablations remove retrieved knowledge or the explicit mobility-reasoning
stage. `no_bottleneck` replays each cycle from the matching `ours` run and
keeps its state, priorities, selected cells, and search outcome, but randomly
matches the idle UAVs to those cells one-to-one. The random branch is not
propagated: the next cycle again starts from the corresponding `ours` state.
Its assignment RNG is independent of the simulator RNG and seeded by the run
seed. The full-method reference is the Exp. 1 `ours` row and is not charged or
run again.

If an LLM output is truncated or unusable, the client makes at most one
additional model call. After two unusable LLM-Direct responses, the baseline
uses a nearest feasible unsearched-cell assignment so that malformed output
does not silently masquerade as a completed policy decision. Transient API
timeouts, connection failures, throttling, and server errors use the separate
transport retry policy.

### Exp. 3: dispatch-batch sensitivity — 40 runs

The fleet stays fixed at `N = 10`; `B` takes every integer value from 3 (the
number of victim groups) through 10. Each setting uses seeds 42–46 and
`max_epochs = ceil(200 / B)`, giving approximately the same maximum number of
UAV-cell assignments. Exp. 3 reports mission completion time and total energy
consumption; it does not use agent inference time as a batch-size outcome.

### Exp. 4: cross-backbone evaluation — 20 runs

The four additional `ours` configurations below use seeds 42–46 and
`N = B = 10`. The DeepSeek-V4-Pro anchor is reused from Exp. 1.

| Provider | Model | Mode |
| :--- | :--- | :--- |
| DeepSeek | `deepseek-v4-pro` | non-thinking; Exp. 1 anchor |
| DeepSeek | `deepseek-v4-flash` | non-thinking |
| Qwen | `qwen-flash` | non-thinking |
| Qwen | `qwen-plus-2025-12-01` | non-thinking |
| Qwen | `qwen3-max-2026-01-23` | non-thinking |

Besides the separate cross-backbone result table, the analysis provides a
qualitative comparison of each backbone's high-priority cells and the
victim groups. A compact heatmap strip shows the seed-42 priority maps at the
first decision (`t = 3600 s`), with the top `B = 10` cells and subgroup
locations marked directly. All backbones therefore receive the same context
and search history in this comparison. The subgroup locations are read from
the simulator only when generating the figure and are not agent inputs.

### Exp. 5: case study — 1 run

The seed-42 `ours` run saves priorities, dispatches, UAV paths, and victim
trajectories for the qualitative terrain/priority/trajectory figure.

The complete formal manifest therefore contains `35 + 20 + 40 + 20 + 1 =
116` run specifications.

## Running the Experiments

### Inspect the formal matrix without API calls

```bash
python3 experiments/manifest.py
```

This command ends with `VALID: 116 unique runs` and prints the stable ID of
each run.

### Run one formal configuration

For example, the following executes only the seed-42 proposed-method row from
Exp. 1 while retaining its checkpoint for safe continuation:

```bash
python3 experiments/exp1_main_comparison.py \
  --methods ours --seeds 42 --max-epochs 40 --parallel 1
```

The ad-hoc `run_experiment.py` remains useful for simulator exploration, but
paper results should be produced by the `experiments/exp*.py` drivers because
they define the formal matrix and stable run identities.

### Run the complete pipeline

```bash
EXP_PARALLEL=16 ./run_all.sh
```

The pipeline runs `exp1 → exp2 → exp3 → exp5 → exp4`, validates all 116
results, and generates the tables and figures. `EXP_PARALLEL` bounds the
number of independent runs, not the number of requests made within one run.
Provider quotas, network capacity, and available CPU/memory may require a
lower value.

Run IDs explicitly contain experiment, method, `N`, `B`, seed, and—where
applicable—provider/model/mode. For example:

```text
exp1_ours_N10_B10_s42_deepseek_deepseek-v4-pro_nonthinking
exp3_ours_N10_B3_s42_deepseek_deepseek-v4-pro_nonthinking
```

This prevents a checkpoint produced for one fleet or batch configuration from
being reused by another. Existing directories whose IDs are not in the
current 116-run manifest are preserved and ignored by formal validation.

Use a driver's `--list-runs` option to inspect exact IDs and `--run-id ID` to
select one run. A completed run is skipped by default. Add
`--rerun-completed` only when that exact completed run is intentionally being
repeated.

### Generated analysis artifacts

After successful validation, `experiments/analyze.py` writes:

- `results/figures/combined_table.md` — Exp. 1 baselines and Exp. 2 LLM variants;
- `results/figures/cross_backbone_table.md` — separate backbone comparison;
- `results/figures/exp3_batch_sweep.pdf` — search time and energy versus `B`;
- `results/figures/exp4_backbone_alignment.pdf` and `.svg` — compact
  initial-priority heatmap strip placed with the backbone table;
- `results/figures/exp5_case_study_current.pdf` — qualitative search trajectory;
- `results/figures/llm_output_quality_by_backbone_table.md` — output parsing
  and fallback statistics.

## Reproducibility

Simulation randomness is controlled by fixed seeds, but fresh model calls are
not guaranteed to reproduce the paper's numbers bit for bit. The external LLM
services can return different outputs for identical prompts even at
`temperature = 0`, and the implementations or serving stack behind a model
identifier can change. Network, proxy, provider queueing, and service load
also affect end-to-end agent computation time. These effects exist under both
serial and concurrent execution; all compared LLM configurations use the same
timing definition, output budget, retry policy, and evaluation seeds.

The source release excludes the original result files, response caches, and
checkpoints. A fresh run therefore evaluates the available provider versions
rather than replaying the original responses.

## Scope and Limitations

The domain knowledge base is an initial implementation limited to the
mobility ranges and SAR heuristics described above. The terrain map, victim
trajectories, sensing, and mission dynamics are simulated rather than derived
from a physical deployment. The results therefore characterise this simulated
setting; validating a broader knowledge base, real geographic data, and
physical UAV experiments remains future work.

End-to-end agent computation time includes provider, network, and proxy
latency. These components vary with service load and concurrent traffic, so
absolute latency is deployment-dependent even when the comparison protocol is
held fixed.
